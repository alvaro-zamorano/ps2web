# patches/ — cambios de F3 al código de Play! (modelo sin fork de GitHub)

El token disponible no puede crear/forkear repos (solo push a repos existentes de Wcoach24),
así que en vez del objeto-fork de GitHub usamos una **serie de patches** que consigue lo que
pide el plan (D10): diffs limpios, revisables y rebasables sobre el commit pinneado de upstream.

## Estructura
- `patches/*.patch`         → se aplican al árbol principal de Play! (`Source/…`, CMake, etc.)
- `patches/codegen/*.patch` → se aplican al submódulo `deps/CodeGen` (Play--CodeGen)

## Cómo se aplican (CI, tras el checkout de Play- @ UPSTREAM.lock)
```
for p in patches/*.patch;         do git -C Play-            apply --index "$p"; done
for p in patches/codegen/*.patch; do git -C Play-/deps/CodeGen apply --index "$p"; done
```
Orden alfabético (prefijo NN-). Cada patch = un sub-hito con nombre claro.

## Generar un patch (flujo de desarrollo)
En un clon de Play- @ UPSTREAM.lock: editar → `git diff > /ruta/ps2web/patches/NN-desc.patch`
(para CodeGen, hacer el diff dentro de `deps/CodeGen`).

## Lección (2026-07-10): CRLF en patches
Algunos ficheros de Play! usan CRLF (p.ej. Source/BasicBlock.h). Editar en modo texto con
python convierte CRLF→LF y reescribe el fichero entero (diff gigante, patch frágil). Editar
esos ficheros en modo BINARIO preservando `\r\n`. Verificar con `git diff --numstat` (líneas
cambiadas deben ser pocas, no ~todo el fichero).

- 13-gl-callcost.patch — **PLAN-DBZ-FLUID Fase 1C.2 (coste por draw call + bisect de diagnóstico)**. Dos partes, ambas `#ifdef __EMSCRIPTEN__`, sin tocar EE RAM (cube golden inmune):
  1. **Quita dos errores GL por draw call** en `DoRenderPass` (~1200 draws/frame en DBZ, hilo GS al 100%): (a) `glTexParameteri` sobre el handle 0 → WebGL lo rechaza con `No texture bound to TEXTURE_2D`; ahora sólo se aplican los parámetros si hay textura ligada. (b) `GL_TEXTURE_SWIZZLE_R` **no existe en WebGL2** (`Invalid enum value`) → la llamada SIEMPRE falló, así que quitarla es behaviour-preserving en wasm. También en `FlipImpl`. ⚠️ Implicación de corrección: `alphaAsIndex` (paletas IDTEX) nunca se aplicó en navegador — candidato a explicar glitches de texturas; arreglarlo va en el shader y es tarea aparte.
  2. **`setGsDiag(n)`** — bisect en runtime (default 0, sólo diagnóstico) para decidir con datos la siguiente inversión grande: `0`=normal, `1`=hace todo el setup de estado + `glBufferData` pero **salta `glDrawArrays`** (aísla el coste de rasterizar), `2`=salta el render pass entero. `gsBusyMsS(0)−gsBusyMsS(1)` = tiempo rasterizando; `gsBusyMsS(1)−gsBusyMsS(2)` = tiempo en estado/upload (lo que atacaría el batching). Distingue **fill-rate-bound** (→ WebGPU/resolución) de **call-overhead-bound** (→ batching + state cache).

- 14-gs-owned-context.patch — **PLAN-DBZ-FLUID Fase 1C.3: el hilo GS es DUEÑO del contexto WebGL (OffscreenCanvas)**. Diagnóstico (docs/PROFILE-DBZ.md §11): con `setGsDiag(2)` (cero draws) el hilo GS seguía ~90 % ocupado. Causa: con `-sOFFSCREEN_FRAMEBUFFER` el contexto vivía en el hilo principal y TODA llamada GL del pthread GS iba proxied; `glTexImage2D/glTexSubImage2D` ≥256 KB, `glGenTextures`, `glDeleteTextures`, `glReadPixels` son round-trips SÍNCRONOS (bloquean el GS hasta que main los sirve) y el resto aloca+postea. Cambios: (1) `-sOFFSCREENCANVAS_SUPPORT=1` + export `_initVmPhase2` (viven en `tools/apply_f2_flags.sh`, no en el patch: `git apply --index` rechaza un fichero que el paso de flags ya modificó); el `CGSHandler` (construido en el hilo EE) pide por proxy al hilo MAIN —único dueño del canvas DOM— que haga el `pthread_create` del GS con `emscripten_pthread_attr_settransferredcanvases("#outputCanvas")` (`Ps2webCreateThreadOnMain`), y `CGSH_OpenGLJs::InitializeImpl` crea el contexto EN el hilo GS → todas las gl* son llamadas directas. (2) OffscreenCanvas solo presenta cuando el worker vuelve a su event loop, así que el `ThreadProc` bloqueante se sustituye por `Ps2webDrain` (tarea en el event loop del worker GS; procesa el mailbox hasta vaciarlo o hasta un flip, entonces cede para que el navegador presente y se re-encola por proxy a sí mismo) + `Ps2webKick` (en `SendGSCall`, tras cada push y ANTES de esperar, encola como máximo una tarea pendiente vía `emscripten_proxy_async`; la espera de completion se hace en `SendGSCall` con un `std::promise` propio). El hilo se mantiene vivo con `emscripten_exit_with_live_runtime()` (`emscripten_unwind_to_js_event_loop` solo NO basta en un pthread: el contador keepalive es 0 y el hilo muere). (3) `initVm` en dos fases: main no puede bloquear mientras la creación del GS está pendiente; la fase 2 (pad/sonido/callbacks, que sí bloquea) la lanza el overlay (`PlayModule.ts`) desde el event loop de JS al ver `getVmInitState()==1` (bloquear DENTRO de una tarea proxied deadlockea: el spin del futex de main no sirve más llamadas proxied por la guarda de recursión, y cualquier printf/fd del EE es una syscall proxied síncrona). Escape hatch A/B en el mismo build: `?gsproxy=1` → ruta antigua. **El patch solo toca ficheros LF** (GSHandler.*, PS2VM.h, ui_js/*): MailBox.* y PS2VM.cpp son CRLF y el conector de GitHub normaliza finales de línea al pushear (un primer intento con hunks CRLF llegó corrupto y falló en `git apply`). Verificado en sandbox (Chromium headless + SwiftShader): cube renderiza, **golden `stateHashAtN=3049433245` intacto**, 0 errores, en ambos modos (36 fps owns vs 27 proxy). Lecciones de emscripten 4.0.1: `emscripten_set_immediate` no funciona en workers (su polyfill hace `postMessage(id,"*")` → "Overload resolution failed"); TODAS las syscalls (fd_read/fd_write/…) desde pthreads son proxied síncronas a main → **las lecturas del ISO (CDVD) desde el EE también** — candidato principal al techo del 65 % (docs/QA-PLAN.md §2.3), siguiente patch.
- 15-disc-io-worker-limiter.patch — **PLAN-DBZ-FLUID Fase 1C.4: lecturas del ISO sin hilo principal + limitador de frames por deadline + métricas del "segundo muro"**. (1) `Js_DiscImageDeviceStream`: upstream hacía por CADA lectura de sector un `MAIN_THREAD_EM_ASM` (proxy síncrono a main) que lanzaba `file.slice().arrayBuffer()` y luego SONDEABA `isDone()` con más llamadas proxied + `usleep(100)`. Ahora `DiscImageDevice.ts` (overlay) arranca un IO worker con el `File` y un `FileReaderSync`; el EE escribe la petición en un bloque de control dentro de la memoria wasm (`getDiscCtrlPtr()`, estático), `futex wake`, el worker lee el slice directamente a memoria wasm y notifica; main no participa. Encima, cache read-ahead de 256 KB en C++ (lecturas secuenciales = memcpy). Fallback automático a la ruta antigua si no hay worker o no responde en 5 s; A/B: `?discproxy=1`. Necesita `wasmMemory` exportado (`apply_f2_flags.sh`). (2) `FrameLimiter`: el algoritmo upstream duerme (objetivo − media de trabajo) DESPUÉS del trabajo y nunca descuenta lo que el sueño se pasó; en un worker un futex con timeout despierta tarde y eso no se recupera. Ahora deadline absoluto (anterior + 1/fps; un despertar tardío acorta la siguiente espera; resync si va >2 frames por detrás) con margen de spin adaptativo (EMA del overshoot, tope 8 ms). A/B: `setLimiterMode(0|1)`, `setFrameLimit(0|1)`. (3) Métricas nuevas: `iopExecMsS`, `spuMsS`, `limiterMsS`, `discMsS`, `discReadsS` y, la importante, **`vblanksPerSec` / `crtFrameRate` / `vmSpeedPct`**: la velocidad REAL de emulación = vblanks de la VM por segundo vs 50 (PAL) / 60 (NTSC). `fps`/`emuSpeedPct` cuentan flips del GS y **subestiman** los juegos que presentan cada 2 vblanks: DBZ BT3 PAL en el menú de idioma marca `emuSpeedPct` 42 % (25 flips/s ÷ 60) cuando `vmSpeedPct` = 100 % (50 vblanks/s). Parte del "techo del 65 %" de QA-PLAN §2.2 era este artefacto de métrica. Verificado en sandbox con el ISO real: DBZ arranca hasta el menú a vmSpeed 100 % (limitador durmiendo ~600 ms/s = 60 % de CPU libre en el hilo EE); cube golden intacto en ambos modos. Solo ficheros LF (los timers del IOP van en `GenericMipsExecutor.h` armados desde `Main.cpp`, los del SPU en `Iop_SpuBase.cpp`, los del limitador en `FrameLimiter.cpp`): `PS2VM.cpp`/`Iop_SubSystem.cpp` son CRLF y el conector no puede pushear CR; además el token del conector no puede tocar `.github/workflows/` (403), así que el CI sigue con `git apply --index` estricto. ⚠️ El deploy del CI está roto desde hoy (`VERCEL_TOKEN` caducado/inválido: el job `deploy` falla y no aparece ningún deployment en Vercel): hay que rotar el secret; mientras tanto se despliega desde el sandbox/conector de Vercel.
